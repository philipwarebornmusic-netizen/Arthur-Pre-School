ärtan – Supabase setup

Configuration
- Project URL and publishable key live in ../supabase-config.js.
- The publishable key is safe for the browser. Never commit a secret/service-role key.
- Authentication uses Supabase email/password accounts.

Database installation or upgrade
1. Open Supabase Dashboard -> SQL Editor -> New query.
2. When upgrading the previous Arthur pilot database, paste and run all of 000_upgrade_from_arthur.sql as a separate query.
3. Open another new query, then paste and run all of schema.sql.
4. Run each numbered migration file in ascending order. Skip only migrations already applied to that database.
5. No seed file is used. The application starts empty and creates real data through onboarding.

Together, the upgrade preflight and schema handle both a new database and the previous Arthur pilot schema. They:
- creates the production tables, indexes and RPC functions;
- installs organization-scoped row-level security;
- supports organization and school creation;
- supports email-bound, single-use invitations for staff and guardians;
- lets guardians maintain, clear, and remove their child's profile notes, health, emergency contacts, and consents after staff has linked the child;
- lets staff and administrators read that child information, including allergies, without editing it;
- provides an official school feed with comments, private parent–staff messaging, atomic staff messages to every guardian of a child, and consent-gated multi-image posts in a private Storage bucket;
- separates guardian-planned attendance from staff-recorded check-in and check-out times;
- lets administrators publish immutable, non-overlapping school terms with weekday hours and closures, then lets guardians save recurring Monday–Friday schedules for their children;
- keeps parent-to-parent messaging and playdate requests off until both parents opt in;
- provides private, same-department birthday invitations with separate mutual opt-in and recipient-isolated RSVP responses;
- removes the known Solgläntan demo organization and exact @arthur.test accounts.

Required Supabase Auth setting
- Set the Site URL to the deployed app origin.
- Add local/deployment redirect URLs if email confirmation is enabled.
- Keep leaked-password protection and email confirmation enabled for production.

Invite-only onboarding
- supabase/009_invite_onboarding.sql and supabase/010_pickup_passes.sql are already applied in production. Do not run them again.
- Deploy previews use the production database.
- The file hashes any existing invitation codes. Previously sent links keep working. It does not delete profiles, children, or guardian links.
- Staff invitations expire after 7 days. Guardian invitations expire after 14 days. Both are single-use.
- The app shows each new link or school code once so it can be copied. It does not send that link itself.

First real account
1. Open the app and create an account.
2. Confirm the email if required, then log in. Supabase Auth sends that confirmation with the project's own email, not a separate paid service.
3. Choose "Jag startar en ny organisation" and provide organization, first school and first department.
4. Add departments on Skolor, then add children under Personer.
5. Invite staff to a school and department, and invite each guardian to one child. Copy the link and send it with the school's existing email or message channel.
6. A school code is optional. A person who uses it stays on a waiting screen with no child data until an administrator approves a department.
7. Guardians request an additional child from the app. Staff approve the request before the child is linked.

Guardian-owned child information
- supabase/011_guardian_owned_child_info.sql is already applied in production. Do not run it again.
- The file does not delete rows or drop columns. It does not touch pickup_contacts, pickup_passes, or pickup_events.
- 010 does not grant staff or admin any write on the child profile, health, emergency contacts, or consents.
- Guardians edit and remove that information. Staff and administrators keep read access. Creating a child, including name and department, stays with staff and administrators. An administrator can move a child between departments and can still delete a child.

Class list and profile photos
- supabase/migrations/015_class_list_photos.sql has not been applied. Do not run it until the class list and profile photos should be activated. Deploy previews use the production database and show that the feature is not activated until then.
- The file creates the private Storage bucket child-photos (not public, 2 MB, JPEG only) and the consent tables. No separate bucket step is required when that insert succeeds. If the storage schema rejects the insert, create a private bucket with that id, the same size limit and image/jpeg, then run the file again.
- Guardians upload, replace and delete <child_id>/profile.jpg. Replacement upserts that same path, so the previous file is overwritten. The app deletes the object through the Storage API. clear_child_photo only checks that the object is gone and then clears photo_path. The SQL does not DELETE from storage.objects, because protect_objects_delete rejects every such statement. Staff and administrators of the child's department can read the photo. Other guardians can read it only when every linked guardian has opted in and the child is still named in the class list.
- Answers are per guardian. A null answer is unanswered, not a no. Any explicit no hides the name immediately. The photo requires yes from every linked guardian. Changes are appended to class_list_consent_events.
- This opt-in is separate from app_images, group_images and social_media. Do not reuse those rows.

Fake Test organization and PreSchool Test preschool
1. Keep this tenant free from real child, health, contact and consent data.
2. Preview the fixed plan from the repository root:
   python3 scripts/provision_test_school.py --plan
3. Set SUPABASE_SERVICE_ROLE_KEY and ARTHUR_TEST_PASSWORD in the local shell. Never write either value to a file or task note.
4. Apply the idempotent plan:
   python3 scripts/provision_test_school.py --apply
5. The command verifies one admin, six parent profiles, and no automatically created child. Each parent registers their own child after login.

Deployment
Serve the repository root as a static site. index.html loads supabase-config.js before app.js. Apply schema.sql and then every unapplied numbered migration before deploying dependent application code.
Production URL: https://artanperschool.netlify.app/
Use this exact origin as the Supabase Auth Site URL and allowed redirect URL.
